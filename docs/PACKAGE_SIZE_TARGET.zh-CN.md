## 1. 目标与口径

本文回答三个问题：优化后各种发布形态大约多大，数字从哪里来，哪些还不能确定。功能、OCR 模型和界面风格不为体积让步，体积只来自移除确证无用的依赖。

体积分为四类，报告时分别给出，不能互相替代：

| 指标 | 含义 | 为什么单独看 |
| --- | --- | --- |
| 下载大小 | 单文件 EXE、安装 EXE、解压 ZIP 三个发布文件的字节数 | 用户实际下载的体积 |
| 便携目录 | 解压版目录内全部文件的合计 | 解压后磁盘占用的上限 |
| 安装后占用 | 安装版装好后程序目录的大小 | 与便携目录接近，另含卸载程序 |
| 单文件释放占用 | 单文件版首次启动释放到缓存目录的内容 | 单文件 EXE 变小不代表运行时占用变小 |

压缩包变小不自动代表便携目录或内存变小，每一类指标都要用新构建单独测量。

## 3. 各阶段预期体积（推算）

本章全部是推算，不是结果。方法：用基线实测值减去可移除文件在原 ZIP 中的压缩载荷。单文件 EXE 与安装器使用各自的压缩算法，实际差额可能与 ZIP 载荷不同，必须用新构建测量后才能写成结论。

### 3.1 阶段 1：统一增强 OCR，移除 SDK / WinRT

- 已测：`Microsoft.Windows.SDK.NET.dll` 与 `WinRT.Runtime.dll` 合计解压 24.23 MiB，原 ZIP 载荷 6.32 MiB。
- 未验证的前提：这两个文件只有在 TFM 或投影开关调整后才会退出发布，仅删除 OCR 代码并不够。TFM 实验完成前，下表都不成立。

| 发布形态 | 基线 | 推算值 | 估计区间 |
| --- | ---: | ---: | ---: |
| 单文件 EXE | 103.99 | 97.67 | 97.0 – 98.5 |
| 安装 EXE | 79.54 | 73.22 | 72.5 – 74.5 |
| 解压 ZIP | 100.84 | 94.52 | 94.0 – 95.0 |
| 便携目录（解压后） | 213.66 | 189.43 | 精确，等于基线减 24.23 |

区间是对压缩差异的粗略估计，不是统计误差。便携目录的差额是文件大小之差，只要这两个文件确实退出发布就成立。

### 3.2 阶段 2：原生 UI Automation，解除 WPF

这一阶段的收益没有测量数据，只能给出上限。`artifacts/publish/win-x64/self-contained` 的目录列表只取了前 40 行，已看到的 WPF 相关候选文件合计约 35.5 MiB（`PresentationFramework`、`PresentationCore`、`D3DCompiler_47_cor3`、`ReachFramework`、`PresentationUI`、`PresentationNative_cor3`、七个主题程序集、`DirectWriteForwarder`、`PenImc_cor3` 等）。

- 按桌面框架整体压缩比 0.41（31.44 / 77.33）折算，压缩后收益上限约 14.5 MiB。
- 这是理论最好情形。WinForms 的真实依赖闭包可能要求保留其中一部分，实际收益可能明显更低，也可能因 SDK 仍带入这些文件而为零。
- 目录列表被截断，托管 UI Automation 相关程序集是否随包发布还没有看到，需要完整文件清单确认。

| 发布形态 | 阶段 1 后 | 阶段 2 理论最好情形 |

## 5. 三种发布形态的大小

三种形态使用不同的打包与压缩方式，同一次依赖变化对它们的影响不同。第 3 章的推算只是用 ZIP 载荷差额近似，本章列出每种形态应当如何单独测量。

### 5.1 汇总

| 形态 | v0.3.13 实测 | 阶段 1 后（推算） | 阶段 2 理论最好情形 | 状态 |
| --- | ---: | ---: | ---: | --- |
| 单文件 EXE | 103.99 | 约 97.7 | 约 83 | 推算，未测 |
| 安装 EXE | 79.54 | 约 73.2 | 约 59 | 推算，未测 |
| 解压 ZIP | 100.84 | 约 94.5 | 约 80 | 推算，未测 |

阶段 2 一列是第 3 章给出的理论上限，不是目标。三种形态的文件集必须一致，只有压缩方式不同。

### 5.2 单文件版

- 构建参数来自 `scripts/publish.ps1`：`PublishSingleFile=true`、`IncludeNativeLibrariesForSelfExtract=true`、`EnableCompressionInSingleFile=true`、`PublishTrimmed=false`。
- 压缩已开启，所以不存在「打开压缩就能再变小」的空间。基线 103.99 MiB 高于 ZIP 与安装 EXE，原因没有测过，不在文档里猜测。
- 实际是否释放原生库取决于打包内容，不能只看开关推断。当前 .NET 10 构建的托盘启动测量没有生成释放文件，指定缓存目录占用为 0；依赖变化后仍需重新测量，下载大小和释放占用分别记录。
- 移除 SDK 投影后，需要同时看下载大小、释放占用、冷启动和热启动。托管程序集变少一般有利于启动，但这是预期，不是结论。

### 5.3 安装版

- 由 `packaging/windows/SnipLite.iss` 生成：`Compression=lzma2`、`SolidCompression=yes`，安装到 `{localappdata}\Programs\SnipLite`，`MinVersion=10.0.19041`。
- 基线 79.54 MiB 是三种里最小的。实际压缩比取决于 Inno Setup 的固实压缩对整个目录的处理，阶段 1 的差额不一定等于 6.32 MiB。
- 可以试 LZMA 字典大小与压缩级别，但 OCR 模型本身是高密度数据，预期收益很小，且会增加安装耗时与峰值内存。没有测量前不写数字。
- 要另外测安装后程序目录的大小，它接近便携目录，而不是下载大小。

### 5.4 解压版

- 基线 100.84 MiB，ZIP 载荷 100.80 MiB，两者几乎相同，说明差额主要来自目录结构开销。
- 解压后目录约 213.66 MiB，是这三项里磁盘占用最大的。便携目录的减少量等于被移除文件的大小，这个数字不依赖压缩算法，是最确定的收益。
- 阶段 1 若两个 SDK 文件确实退出，便携目录应从 213.66 降到约 189.4 MiB。这仍然取决于 TFM 实验是否成立。

### 5.5 影响三种形态的共同因素

| 因素 | 影响 | 处理方式 |
| --- | --- | --- |
| SDK 投影是否退出 | 决定阶段 1 是否有收益 | TFM 实验，检查 `project.assets.json`、`.deps.json` 与发布目录 |
| WPF 文件是否退出 | 决定阶段 2 的收益，不确定性最大 | 原生 UIA 验收后，用完整依赖闭包审计 |
| 依赖版本变化 | 升级运行时或 SDK 会改变文件集和大小 | 瘦身期间不升级，升级后重新审计 |
| 文档与许可证 | 约 1.24 MiB，三种形态都包含 | 保留，不作为优化对象 |

### 5.6 本章不做的事

- 不为某一种形态单独删文件，三种形态使用同一份发布目录。
- 不用解压版的变化直接推断单文件或安装版的结果，每种形态都要重新测量。
- 不把单次构建的差额写成稳定数字，至少重复构建一次确认大小可复现。

## 6. 进一步压缩的路径与体积下限

本章回答两件事：阶段 1、2 之后还有哪些路可走，以及自包含包的体积大致能压到多少。下限是依据已测压缩载荷的推算，不是承诺。

### 6.1 体积下限的推算

自包含发布必须带上的部分，按基线的 ZIP 压缩载荷（MiB）：

| 部分 | ZIP 压缩载荷 | 依据 |
| --- | ---: | --- |
| OCR 模型 | 25.76 | 完整保留，不降精度 |
| OCR 引擎 | 0.67 | 保留 |
| .NET 基础运行时 | 35.11 | 自包含必需，仅有证据的附属组件可审计 |
| 文档、许可证、主程序、二维码库 | 约 1.51 | 0.90 + 0.37 + 0.24 |
| 小计（不含 WinForms） | 约 63.05 | 以上之和 |
| WinForms 自身 | 未测 | 桌面框架 31.44 中 WinForms 与 WPF 各占多少没有数据 |

因此自包含 ZIP 的下限约等于 63 MiB 加上 WinForms 的压缩载荷。WinForms 的份额要在原生 UIA 验收、`UseWPF` 关闭之后，用实际发布结果才能得到。此前口头给出的「70–80 MiB」只能当作粗略区间，不是目标。

### 6.2 可继续评估的路径

| 路径 | 预期收益 | 代价与风险 | 结论 |
| --- | --- | --- | --- |
| 阶段 2 之后审计 `Microsoft.DiaSymReader.Native`、`Microsoft.VisualBasic.*`、`Microsoft.CSharp` 等附属文件 | 解压合计约 4.6 MiB，压缩后更少 | 特定功能启动才缺程序集或原生库 | 证据不足就保留，逐项回归后才允许排除 |
| 安装器调整 LZMA 字典与压缩级别 | 预期很小，OCR 模型已是高密度数据 | 安装耗时和峰值内存增加 | 只测量，不预先写数字 |
| 另外提供依赖运行时的轻量版 | 去掉 .NET 运行时后，下载体积会明显更小，具体数字需另测 | 用户需要自行安装对应的 .NET Desktop Runtime | 可作为独立下载补充，不计入自包含包的瘦身成果 |
| 彻底原生化（原生 Win32 窗口加自绘前端） | 可能去掉 .NET 运行时 | 见 6.4 | 本轮不承诺，需要另立原型验证 |

### 6.3 本轮明确不采用

- 全量 `PublishTrimmed`：WinForms 与 WPF 的框架级裁剪存在官方限制，当前脚本也显式关闭。
- Native AOT：不是当前项目可直接打开的发布开关，需要独立技术验证。
- 删除来源不明的 DLL，或发布后手工删文件：三种形态会不一致，缺失依赖会在运行时才暴露。
- 降低模型精度、更换更弱的 OCR 模型、改成在线 OCR 或首次联网下载模型：与离线可用和识别质量的要求冲突。
- 删除多语言说明、预览图和许可证：合计约 1.24 MiB，不值得牺牲八语言使用说明和合规声明。
- 为追求「零 WPF 文件」而强删 WinForms 实际依赖的文件。

### 6.4 彻底去掉 .NET 的边界

自行绘制相同外观在技术上可行，但保留 WinForms 宿主就仍需要 .NET。要真正去掉 .NET，需要同时解决：

1. 窗口层：输入法、剪贴板、拖放、DPI、无障碍、托盘与全局快捷键。
2. OCR 入口：当前使用的是 SimdPaddleOCR 的 .NET 入口，必须先验证是否有可独立部署的原生等价实现。
3. 只换窗口层、后台仍启动 .NET 的 OCR 进程，未必减少总分发体积。

无论如何，OCR 模型约 25.76 MiB 的压缩载荷是不可压缩的部分。完成上述验证之前，不承诺几 MiB 的包体，也不承诺可无成本复用现有识别代码。

### 6.5 取舍顺序

先做确定性收益（阶段 1 的 SDK / WinRT），再做收益不确定的阶段 2，再决定附属文件审计和打包参数。只有在这些完成并有实测数字后，才评估是否值得投入原生化。每一步收益都用新构建测量，不用理论差额代替。

## 7. 测量与验收方法

本章规定体积数字如何产生。没有按本章方法测得的数字，只能标为推算。

### 7.1 每个阶段必须保存的记录

- 源码提交、.NET SDK 与运行时版本、依赖包版本、完整构建命令。
- 发布目录的逐文件清单：相对路径、字节数、SHA256。
- `.deps.json`、`project.assets.json`，以及隐式 SDK 引用（例如 `Microsoft.Windows.SDK.NET.Ref`）的版本。
- 三种发布形态的文件大小：单文件 EXE、安装 EXE、解压 ZIP。
- 便携目录合计、安装后程序目录合计、单文件首次启动后的释放目录合计。
- 冷启动与热启动耗时、首次与再次 OCR 耗时、稳定后的内存占用。

### 7.2 构建与输出隔离

- 实验产物输出到 `.local/package-size-optimization/<阶段>/`，不覆盖 `artifacts/` 下的 v0.3.13 对照产物。
- 不运行 `scripts/clean.ps1`，它会清空整个 `artifacts/`，对照产物会丢失。
- 当前 `scripts/publish.ps1` 和 `release.ps1` 支持 `-OutputRoot`，本轮使用独立 `.local/` 输出根目录；也可直接调用同参数的 `dotnet publish -o`。默认 `artifacts/` 仍保留历史基线，不覆盖。
- 正式发布前再通过 `scripts/release.ps1` 走完整流程，实验构建不作为发布件。
- 测试用的配置目录和模型缓存与用户正在使用的安装隔离，不改动现有配置。

### 7.3 测量规则

- 同一台机器、同一份样例输入、同一套发布参数下比较新旧版本。
- 启动冷、热各至少 5 次；首次与再次 OCR 各至少 10 次；报告中位数和范围。
- 同时标注冷启动的定义、模型是否已加载、单文件缓存是否已存在。
- 每个大小至少重复构建一次，确认可复现，再写入报告。
- 拟定的人工复核阈值：启动或 OCR 中位耗时相对对照增加超过 10% 且绝对增加超过 50 ms，或稳定后内存持续增长。阈值用于发现回归，不因单次抖动直接判定失败。

### 7.4 依赖是否真的退出的核对

阶段 1 与阶段 2 的收益都取决于文件是否真的不再发布，核对顺序如下：

1. 查 `project.assets.json`，确认投影包不再出现在还原图里。
2. 查发布目录和 `.deps.json`，确认目标文件不存在。
3. 查单文件 EXE 的内容清单，确认文件没有被打进 bundle。
4. 对三种形态分别执行，不能只检查解压版。

某个文件仍被引用时，先记录引用来源并修订方案，不使用发布后强删来掩盖。

### 7.5 隔离环境验收

- 在没有 .NET SDK、也没有预装 .NET Desktop Runtime 的干净 Windows x64 环境中验证三种包，覆盖 Windows 10 目标下限和 Windows 11。
- 解压版完整解压后运行；安装版验证安装、升级、卸载并保留用户数据；单文件版验证首次释放、再次启动、离线 OCR 以及清理缓存后重启。
- 在主机 SDK 环境里测通过，不能代替这一项。
- 没有可用的干净环境时，报告写明尚未完成，不把静态依赖检查写成整体验收通过。

### 7.6 功能回归（体积变化不得带来功能变化）

- OCR：中英混排、小字号、浅深背景、方向文字、空白图、大图；失败后可重试，空结果与失败有不同提示。
- 贴图 OCR 失败不覆盖剪贴板；翻译在 OCR 失败时不发请求。
- 自动框选：Win32 子控件、浏览器页面、Electron 内容，仅在阶段 2 之后作为必测项。
- 旧配置：全新配置、旧版增强 OCR、旧版 Windows OCR、异常的 OCR 字段，加载后其他设置与翻译密钥不变。
- 界面：八语言、浅深主题、100% / 150% / 200% DPI、多显示器。

## 8. 风险与不承诺事项

本章说明本文不承诺什么、哪些收益必须实测后才能确认，以及出现问题时的停止与回退条件。

### 8.1 不承诺的事项

- 不承诺最终体积达到 50 MiB 或任何其他固定数字。第 6 章的下限只是推算，且缺少 WinForms 自身的压缩载荷。
- 不承诺阶段 2 一定有收益。SDK 仍可能带入 WPF 文件，WinForms 也可能真实依赖其中一部分。
- 不把第 3、5 章的推算值写进发布说明、README 或对外宣传，直到取得按第 7 章方法测得的数字。
- 不承诺三种形态的减少量一致。单文件、安装器和 ZIP 的压缩方式不同。
- 不承诺启动耗时或内存下降。体积变小不自动带来这两项变化。
- 不承诺能彻底去掉 .NET。该方向需要另立原型验证，见 6.4。

### 8.2 必须实测才能确认的收益

| 项目 | 当前状态 | 确认方式 |
| --- | --- | --- |
| 两个 SDK 文件是否退出发布 | 已确认目录及单文件均不包含 | 关闭隐式 SDK 投影，TFM 和最低系统版本不变 |
| 阶段 1 代码能否编译、自检通过 | 已通过 | 编译、单引擎 OCR/旧字段兼容烟测通过 |
| 三种形态的实际下载大小 | 已实测并重复构建 | 见 7.7 及结果报告的字节数、SHA256 |
| WPF 文件的真实可移除范围 | 已验证 SDK 自然移除；未手动删 DLL | 完整发布清单、单文件清单及自包含回归 |
| 单文件释放占用与启动耗时 | 基线待补测 | 对旧版和新版用同一方法测 |

更新：上一行的本机测量已补齐，使用新缓存路径和重复进程启动，不等同于重启系统后的完全冷启动；详细范围及局限见最新验收记录。

### 8.3 风险与停止条件

| 风险 | 应对 | 停止或回退条件 |
| --- | --- | --- |
| 删除系统 OCR 后增强引擎失败没有退路 | 失败会提示，可重试，不再被当成空结果 | 失败被误报为空结果，或导致程序退出 |
| SDK 投影仍被隐式引用 | 查 TFM、还原图和程序集引用 | 只能靠发布后删除必要文件才能达成体积 |
| 修改 TFM 影响最低系统版本 | 保持 `SupportedOSPlatformVersion` 与安装器 `MinVersion` 为 10.0.19041 | 声明的最低版本高于实际可运行版本 |
| 原生 UI Automation 的 COM 声明有误 | 用 SDK 定义生成并核对，先做独立原型 | 崩溃、内存破坏或难以解释的调用失败 |
| 控件级自动框选退化为整窗 | 同一点与旧版对照，用真实应用验证 | 退化无法修复时停在阶段 1，保留 WPF |
| WPF 或其他文件被排除后功能缺失 | 规则与依赖版本绑定，逐项回归 | 某功能启动时才报缺程序集或原生库 |
| 三种形态的文件集不一致 | 排除规则在生成目录之前执行 | 只有解压版被精简 |

### 8.4 回退

- 每个阶段单独提交，出问题只回退该阶段。回退时同时恢复相关的引用、文案和打包规则，不留下旧代码加新精简规则的组合。
- 旧配置字段 `OcrEngine`、`OcrLanguage` 保留一个迁移周期，只加载不再读取。降级到 v0.3.13 前先备份配置，不要只依赖可能被后续保存覆盖的单份备份。
- 实验构建不覆盖用户配置和现有安装。需要验证迁移时，先保存独立的配置快照。
- 未通过整体验收，不合并主分支，不复用 v0.3.13 的标签，不自动发布实验构建。
